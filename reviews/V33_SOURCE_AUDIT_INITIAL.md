The revised runner now verifies the post-state and records disposition/reason (`package/civilian/v3_runner.py:200`, `:202`, `:207`, `:213`, `:242`, `:252`, `:297`). This closes the runner omission, but does not yet close end-to-end masking in the reviewed revision.

`package/civilian/counterfactual_pairs.py:611` detects unresolved dispositions, while `:658` defines trace validity solely by absence of an execution exception. `:1001` checks that trace flag, `:1017` marks the pair valid, and `:1044` records unresolved counts without invalidating it. `package/civilian/gain_oracle.py:761` verifies unresolved-count consistency, then `:798` still returns a valid recomputation. `package/civilian/v3_shards.py:55` permits any such valid label/oracle pair into the ordinary-state summary. Therefore a numerically reproducible rollout with unresolved safety can satisfy the 30/30 training gate despite the protocol's unknown masking requirement (`protocols/V33_CIVILIAN_SEARCH_RESCUE.md:23`, `:29`).

Required closure: retain unresolved/unknown receipts and raw trajectories, propagate an explicit masking reason through branch/pair/label and the independent oracle, and prove that the state cannot contribute to either ordinary class. A live receipt with `resolved=false` must not evade this rule merely because the separate disposition field is absent. Verify actual before/after state, not only receipt shape.

### R2 — split/cooperative search completion loses dependent rescue discovery (REPAIR, high)

Rescue obligations reference the original search ID (`package/civilian/v33_scenarios.py:113`). Split/cooperate creates new physical child IDs (`package/civilian/event_environment.py:1606`, `:1611`) and marks the original task `split_parent` (`:1646`). The base simulator reveals demands only where `hidden.discovered_by == completed task_id` (`package/civilian/relief_env.py:916`). Physical children finish under their new IDs; no demand references those IDs. The wrapper aggregates parent completion (`package/civilian/event_environment.py:1978`) and emits `logical_task_completed` (`:2035`), but does not invoke parent-level discovery. Thus a logically completed search can permanently leave its rescue unknown. This changes the intended search→rescue causal dynamics and the gain labels for these legal candidate actions.

The existing regional regression validates logical completion/reward in the older 30-platform fixture (`package/tests/test_v3_regional_execution.py:29`, `:209`, `:279`, `:319`), so it does not cover this V3.3 dependency.

Required closure: use one causally correct logical-parent completion transition to reveal dependent demands exactly once, preserving report delay, raw discovery events and parent identity. Demonstrate no reveal after only one child finishes, and reveal after both children finish, for both split and cooperate. Then run independent gain recomputation on the affected trace.

## Limitations and resolved/nonblocking notes

- Local protocol initially differed from the approved archive protocol (incorrectly saying rescue appears when its search is discovered and omitting the shared dependency-universe rule). The coordinator synchronized it during review. Both copies now hash to `e175194c9cb1cae652d377177a635ff19da81e2493ef2209b8f9edb0ae1cd0c6`; this documentation discrepancy is closed.
- Cancellation is absent from the V3.3 event-slot design (`v33_scenarios.py:120`). The inherited generic path unconditionally changes even completed ordinary tasks to cancelled (`event_environment.py:1850`, `:1859`), while completion scoring tests status (`cost_accounting.py:98`). Cancellation behavior is **not certified** and must be repaired/reviewed before adding such a condition. It does not block the frozen seven V3.3 conditions by itself.
- `current_binding().evidence_sha256` hashes only baseline provenance (`v3_shards.py:126`); it does not bind focused raw evidence/tests/protocol. The final release manifest must separately bind those artifacts. The present audit JSON provides inspected-file hashes but does not replace a final freeze.
- A successful `verify` command can mean only that the shards found are intact; `verify_run` returns the count found and does not enforce a complete expected run (`v3_shards.py:307`). Completion must be established against the required manifest/registry.
- Final readiness remains REPAIR until R1, R2, R3 are closed with the changed files and primary evidence rereviewed. No performance, safety percentage, 30/30 gate attainment, model-training success, or generalization claim is accepted here.
